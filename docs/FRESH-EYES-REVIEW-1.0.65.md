## A — چرا برنامه سنگین حس می‌شود

### A1. ‏۶۲٪ بدنهٔ `/api/market` فقط تکرارِ نامِ ستون است

```
پاسخِ واقعی           ۷٫۱۸ MB   (۵۴۲۷ ردیف × ۷۲ فیلد)
فقط نامِ کلیدها        ۴٫۴۲ MB   ← ۶۲٪ بدنه
همان داده، ستونی       ۲٫۷۶ MB   (−۶۲٪)
gzip فعلی             ۹۴۸ KB
gzip ستونی            ۶۴۷ KB   (−۳۲٪)
```

هر ردیف ۷۲ بار رشتهٔ `"month_avg_vol":` و `"dist_min30_pct":` را با خودش حمل
می‌کند؛ ۵۴۲۷ بار. شکلِ ستونی (`{"columns":[...], "rows":[[...],...]}`) همان
داده را با یک‌بار نوشتنِ نام‌ها می‌دهد.

این تغییر دو نقطه دارد: `_build_market_response` در `api/market.py` و یک تابعِ
کوچکِ «ستونی → آبجکت» درِ `useMarketFeed`/`http.ts`. قراردادِ zod دست‌نخورده
می‌ماند اگر بازسازی قبل از `safeParse` انجام شود — یا بهتر، zod روی خودِ شکلِ
ستونی نوشته شود و بازسازی اصلاً لازم نشود.

### A2. هر پولِ تابلو ~۱۲۰ms نخِ اصلیِ مرورگر را می‌بندد

اندازه‌گیری روی همان بدنهٔ ۷٫۱۸MBِ واقعی:

```
JSON.parse                     ۴۳٫۰ ms
MarketFeedSchema.safeParse     ۳۳٫۰ ms
replaceEqualDeep (TanStack)    ۴۴٫۵ ms   ← حتی وقتی هیچ بایتی عوض نشده
                               ───────
                              ۱۲۰٫۵ ms  هر ۵ ثانیه
```

روی WebView2 و CPUِ کاربر این عدد راحت ۲٫۵–۳ برابر می‌شود. این دقیقاً همان
«~۷۵٪ یک هسته» است که خودتان در `marketHours.ts` یادداشت کرده‌اید.

دو اصلاحِ یک‌خطی:

- **`structuralSharing: false`** روی `useMarketFeed`. اشتراکِ ساختاری برای
  ۵۴۲۷ آبجکتِ ۷۲ فیلدی یعنی ~۳۹۰٬۰۰۰ مقایسهٔ عمقی در هر پول — و چون
  `http.ts` خودش با ETag/۳۰۴ همان *ارجاعِ قبلی* را برمی‌گرداند، وقتی داده
  عوض نشده اصلاً به اینجا نمی‌رسد. پس آن ۴۴٫۵ms فقط وقتی خرج می‌شود که داده
  *واقعاً* عوض شده — یعنی همان لحظه‌ای که هرحال باید دوباره رندر شود. سودِ
  خالص: ۴۴٫۵ms.
- **اعتبارسنجیِ نمونه‌ای به‌جای کامل**: قراردادِ zod روی پاکتِ پاسخ + چند ردیفِ
  اول به همان اندازه «سیگنالِ خراب را می‌گیرد»، ولی ۳۳ms را به <۱ms می‌رساند.
  (zod v4 خودش سریع است؛ مسئله ۵۴۲۷ بار اجراست.)

### A3. سرور هر ۵ ثانیه تابلو را بازمی‌سازد، حتی وقتی هیچ‌کس نگاه نمی‌کند

```
warm_market_cache()  اولِ کار ۱۶۹۰ ms  ·  گرم ۴۲۰ ms
GZip روی همان بدنه            ۱۰۱ ms  (در برابر ۱۱ ms بدونِ فشرده‌سازی)
```

`_board_tick_loop` در `app.py` هر ۵ ثانیه پس از یک تیکِ موفق
`_kick_market_rebuild()` می‌زند → ۴۲۰ms ساختِ بدنه + ۱۰۱ms فشرده‌سازیِ دوباره.
یعنی **~۰٫۵ ثانیه CPU در هر ۵ ثانیه ≈ ۱۰٪ یک هسته، پیوسته** — چه پنجره باز
باشد چه مینیمایز، چه کاربر روی تبِ تابلو باشد چه روی تبِ بنیادی.

و این کار **اضافی** است: `/api/market` از قبل stale-while-revalidate دارد
(`_market_from_cache` + `_MARKET_STALE_CEILING` + قفلِ تک‌نفره). تنها دلیلِ
وجودِ kick این است که `MARKET_CACHE_TTL = 60` از ریتمِ ۵ ثانیه‌ایِ فرانت
کندتر است.

**راهِ ساده:** زمانِ آخرین درخواستِ واقعیِ `/api/market` را نگه دارید و فقط
وقتی kick بزنید که مشتری‌ای در ~۳۰ ثانیهٔ اخیر پرسیده باشد:

```python
# api/market.py
_LAST_CLIENT_GET = 0.0          # در route ست می‌شود
def client_is_watching(window=30.0):
    return time.time() - _LAST_CLIENT_GET < window

# app.py, _board_tick_loop
if _ts.tick_live() and market.client_is_watching():
    market._kick_market_rebuild()
```

پنجرهٔ بسته/مینیمایز/تبِ دیگر → صفر بازسازی. رفتارِ کاربرِ فعال بدون تغییر.

### A4. سه تعریفِ متفاوت از «ساعتِ بازار» در یک برنامه

| جا | پنجره | چه چیزی را می‌راند |
|---|---|---|
| `mstat_engine.in_trading_session` | ۰۹:۰۰–۱۳:۰۰ | حلقهٔ سینکِ کاملِ ۹۰ ثانیه‌ای |
| `test_tsetmc.tick_live` | ۰۸:۵۵–۲۰:۰۰ (نوشتنِ کامل تا ۱۲:۳۰) | تیکِ ۵ ثانیه‌ای |
| `frontend/shared/lib/marketHours.ts` | ۰۸:۴۵–۱۲:۳۰ | ریتمِ پولینگِ فرانت |

پیامدهای واقعی:

- ‏۰۸:۴۵–۰۹:۰۰ — فرانت با ریتمِ سریع می‌پرسد، ولی حلقهٔ سینکِ کامل هنوز خواب است.
- ‏۱۲:۳۰–۱۳:۰۰ — فرانت به ریتمِ ۵ دقیقه‌ای رفته، ولی بک‌اند هنوز سینکِ کامل +
  تیکِ ۵ ثانیه‌ای + بازسازیِ کش می‌زند. CPU برای داده‌ای خرج می‌شود که هیچ‌کس
  نمی‌خواند.

یک ثابتِ مشترک (بک‌اند منبع، فرانت از `/api/market/sync-state` یا یک ثابتِ
تولیدشده بخواند) هر سه را یکی می‌کند.

### A5. حافظهٔ فرآیندِ بک‌اند: ۳۴۸MB

```
RSS پس از ۶ دقیقه و چند درخواست   ۳۴۸ MB
```

تفکیکِ سهمِ import‌ها (اندازه‌گیریِ جدا):

```
پایتونِ خالی                 ۸٫۰ MB
+ numpy                     ۱۵٫۸ MB
+ pandas                    ۵۵٫۸ MB   ← pandas تنهایی ۴۰MB
+ fastapi/uvicorn           ۷۶٫۸ MB
```

بقیه: بدنهٔ ۷٫۵MBیِ کش (دو نسخه حینِ بازسازی)، `CHART_CACHE`/`MA_CACHE`/
`PATTERNS_CACHE`/`FTS_ANALYSIS_CACHE` (سقفِ ۳۰۰۰ ورودی)، و
`PRAGMA mmap_size=268435456` که صفحاتِ نگاشته‌شدهٔ بانک را به RSS می‌آورد.

pandas در `api/market.py` و `tape_flags.py` عمیقاً استفاده شده، پس حذفش «ساده»
نیست — ولی همین pandas+numpy در بستهٔ PyInstagram/PyInstaller هم ده‌ها مگابایت
به نصاب اضافه می‌کند. اگر روزی سبک‌سازیِ بزرگ خواستید، این تنها نقطه‌ای است که
ده‌ها مگابایت یک‌جا آزاد می‌کند. کارِ کوچکِ همین حالا: `mmap_size` را پایین
بیاورید یا فقط روی اتصالِ خواندنیِ سنگین بگذارید، نه روی هر اتصال.

### A6. `get_db()` در هر درخواست DDL اجرا می‌کند

```
get_db()        ۰٫۴۷ ms
connect خالی    ۰٫۰۲ ms      ← ۲۳ برابر
```

هر اتصال (یعنی هر درخواستِ API) این‌ها را دوباره می‌زند: ۵ `PRAGMA`،
۲ `CREATE INDEX IF NOT EXISTS`، `ensure_market_schema` + `ensure_selection_schema`
+ `watchlist_store.ensure_table` + `mstat_engine.ensure_schema` (هر کدام
`PRAGMA table_info` + `CREATE TABLE`/`ALTER`)، و `fts_engine.register_sql`.

روی SSDِ لینوکس نیم میلی‌ثانیه است؛ روی ویندوز با آنتی‌ویروسِ فعال چند برابر.
اصلاحش کاملاً بی‌خطر است چون همهٔ این کارها idempotent‌اند:

```python
_SCHEMA_READY = False
def _ensure_schema_once(conn):
    global _SCHEMA_READY
    if _SCHEMA_READY: return
    ...  # همان بدنهٔ فعلی
    _SCHEMA_READY = True
```

فقط PRAGMAهای per-connection (`journal_mode`, `cache_size`, `temp_store`,
`mmap_size`) و `register_sql` باید بمانند.

### A7. هر استارت یک `Get-CimInstance Win32_Process` می‌زند

`api/_sync_market.py::_market_sync_alive` هنوز PowerShell را با `timeout=15`
صدا می‌زند تا دنبالِ پروسهٔ `test_tsetmc` بگردد. ولی خودِ فایل بالای همان تابع
توضیح می‌دهد که سینک دیگر پروسهٔ جدا نیست و درونِ همین فرآیند با
`_MARKET_SYNC_LOCK` اجرا می‌شود. `Get-CimInstance Win32_Process` روی ویندوز
معمولاً ۰٫۵ تا ۳ ثانیه طول می‌کشد. آن ۹ خط `try/subprocess.run(...)` حذف‌شدنی
است؛ خطِ آخر (قفل) خودش پاسخِ درست را می‌دهد.

ضمناً همان خطِ آخر خواندنی نیست و بهتر است صریح شود:

```python
def _market_sync_alive() -> bool:
    if _MARKET_SYNC_LOCK.acquire(blocking=False):
        _MARKET_SYNC_LOCK.release()
        return False
    return True
```

### A8. `python app.py` دو بار سینکِ بازار را راه می‌اندازد

در `__main__` (خطِ ~۳۴۵) یک نخِ `_sync_market_on_start` ساخته می‌شود، و بلافاصله
`uvicorn.run("app:app")` هوکِ `@app.on_event("startup")` را صدا می‌زند که
**دوباره** همان را می‌سازد. `_market_sync_alive` معمولاً دومی را می‌گیرد، ولی
این یک مسابقه است نه یک تضمین — و دقیقاً همان مسابقه‌ای که A7 را کُند می‌کند.
نخِ داخلِ `__main__` حذف‌شدنی است؛ هوکِ استارت هر دو مسیر (`app.py` و
`start_dashboard.py`) را پوشش می‌دهد و کامنتِ خودِ هوک هم همین را می‌گوید.

زمان‌بندیِ واقعی روی همین ماشین — همه ارزانند:

```

```

پیشنهاد: جابِ `js-syntax` را با یک جابِ `frontend` جایگزین کنید که همین سه را
بزند. خالص: یک جابِ بی‌فایده برداشته می‌شود، یک جابِ واقعی جایش می‌آید.

### C3. `requirements.txt` فقط numpy/pandas را pin کرده

`fastapi`، `uvicorn`، `requests`، `httpx`، `orjson`، `pywebview`، `pythonnet`
همه شناورند و CI موقعِ ریلیز آخرین نسخه را نصب می‌کند. یعنی یک تغییرِ بالادستی

بقیه یا استفاده از `requirements.lock` طبیعی‌ترین ادامه است.

## E — ریزه‌کاری‌ها (هر کدام چند خط)

**E1. مقایسهٔ پیشوندی در `spa_catch_all`** (`app.py`) —
`candidate.startswith(base)` یعنی مسیری مثل `frontend/dist-old/...` هم قبول
می‌شود. `..` را `normpath` می‌گیرد، پس رخنهٔ واقعی نیست، ولی درستش یک خط است:

```python
if os.path.commonpath([candidate, base]) == base and os.path.isfile(candidate):
```

**E2. `@app.on_event("startup")` منسوخ است** — FastAPI مدت‌هاست
`lifespan=` را می‌خواهد. کلِ آن تابعِ ۱۵۰ خطی یک‌جا به یک
`@asynccontextmanager` منتقل می‌شود و در ضمن مسیرِ خاموش‌شدنِ تمیز
(`shutdown`) را هم به شما می‌دهد — که الان وجود ندارد: شش نخِ daemon هرگز
سیگنالِ توقف نمی‌گیرند.

**E3. تنها فایلی که پایتونِ ۳٫۱۱ نمی‌تواند parse کند** —
`tools/chart_diff.py:43` از f-stringِ تودرتو با همان نوعِ کوتیشن استفاده کرده
(PEP 701، فقط ۳٫۱۲+). CI روی ۳٫۱۲ است پس سبز می‌ماند، ولی ۹۷۶ فایلِ دیگر روی
۳٫۱۱ کامپایل می‌شوند و این یکی نه. دو کاراکتر اصلاح می‌خواهد.

**E4. `test_tsetmc.py` در ریشه، نامش مثلِ فایلِ pytest است ولی موتورِ
همگام‌سازیِ ۱۸۱۰ خطیِ TSETMC است.** خودِ `REPO_MAP.md` با ⚠ علامتش زده. کنارش
`test_symbol_aliases.py` هست که *واقعاً* ۷ تستِ pytest دارد. یعنی یک `pytest`
سادهٔ ریشه، موتورِ شبکه را import می‌کند. نامِ `tsetmc_sync.py` این ابهام را
برای همیشه می‌بندد (یک `git mv` + ۶ ارجاع).

**E5. ‏۴۹۶ تا `except Exception` که ۹۶ تایشان `pass` خالی‌اند، و ۳۹۴ تا
`print()` در `api/` و ریشه.** هیچ `logging` وجود ندارد، پس لاگِ عیب‌یابی
سطح‌بندی ندارد و نمی‌شود فیلترش کرد. یک `logging.getLogger(__name__)` و
جایگزینیِ مکانیکیِ `print` → `log.info/warning` کارِ یک sedِ دقیق است و لاگِ
کاربر را از «هرچه چاپ شد» به «هرچه مهم بود» می‌برد.

زودتر می‌رسید قفل را می‌گرفت. در ۳ اجرا هر دو ترتیب دیده شد:


نتیجه در هر دو حالت یکی بود (قفل درست کار می‌کرد و همیشه فقط **یک** سینک
اجرا می‌شد)، ولی مسیر قطعی نبود. حالا هوک مستقیم و هم‌زمان صدا می‌شود و
پیش از ساخته‌شدنِ نخِ حلقه تمام می‌کند، پس ترتیب همیشه یکسان است.

### یک تغییرِ معناییِ صادقانه

با `test_tsetmc` در خطِ فرمان می‌گشت. نسخهٔ جدید فقط قفل را می‌بیند. برنامه
