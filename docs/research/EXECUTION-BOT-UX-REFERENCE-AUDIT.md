## ۱. خلاصهٔ مدیریتی و بیان مسئله (Executive Summary)

واسط کاربری فعلی BorsTerminal دو قابلیت حیاتی معاملاتی—یعنی **سفارش سریع / سرخطی (Fast Order / Sarkhati)** و **ربات معاملاتی (Trading Bot)**—را در نامناسب‌ترین و غیرقابل‌کشف‌ترین نقاط برنامه پنهان کرده است:
1. **پنل سفارش سریع (`ExecutionPanel.tsx`)** به عنوان یک بلوک آکاردئونی جمع‌شده با پیش‌فرض بسته (`useState(false)`) در انتهای زبانهٔ پروندهٔ نماد در دیده‌بان بازار (`WatchSummaryPanel.tsx:16,95` روی مسیر `/watch`) مدفون شده است. دسترسی به آن نیازمند ورود به دیده‌بان، کلیک روی نماد، باز کردن تب فرعی و فشردن دکمهٔ بازشو است.
2. **ربات معاملاتی (`BotPanel.tsx`)** به عنوان یک جعبه در انتهای صفحهٔ پرتفوی (`PortfolioPage.tsx:427`) زیر جداول دارایی و واچ‌لیست رها شده و طبق یادداشت طراح قبلی با فرض نادرست «ربات همین‌جا: کاغذی، دستی و با یک سطر وضعیت—نه صفحهٔ جدا» طراحی شده است.

این چیدمان با استانداردهای ترمینال‌های معاملاتی حرفه‌ای سازگار نیست. با این حال، زیرساخت بک‌اند BorsTerminal (`api/execution.py`, `api/bot.py`, `execution_service.py`, `execution_ledger.py`, `execution_easytrader.py`) از منظر انضباط مالی، مدیریت ریسک، ثبت وقایع لجر (Append-only Ledger) و عدم ارسال دادهٔ جعلی به کاربر، یکی از امن‌ترین و سخت‌گیرانه‌ترین پیاده‌سازی‌های موجود در پلتفرم‌های ریتیل است.

این سند بر اساس شواهد ملموس کد تاریخی (کامیت `5307a795`) و بررسی ۵ پروژه متن‌باز مرجع جهانی و محلی، معماری دو محیط کاری درجه‌یک مستقل را تعریف می‌کند:
* **محیط مدیریت و اجرای سفارش سریع (`#/execution`)**: مجهز به برچسب‌های شفاف وضعیت کارگزاری، اعتبارسنجی پیش‌فرود (Preflight)، پیش‌نمایش بدنه، انطباق وضعیت سفارش (Reconcile)، وضعیت صادقانهٔ صف (`—` در صورت عدم پشتیبانی) و لجر پایدار.
* **محیط پایش و کنترل ربات معاملاتی (`#/bot`)**: مجهز به تمایز سخت‌گیرانهٔ محیط کاغذی و زنده (Paper vs. Live)، نمایش موانع سه‌گانهٔ اجرای زنده، پایش تصمیمات و منطق سیگنال‌های قیف FTS، تاریخچهٔ کامل نشست‌ها و کلید قطع اضطراری سخت‌افزاری (Kill-Switch).

## ۴. انطباق ایمنی بک‌اند و معماری کارگزاری (Safety & Broker Reconciliation)

معماری اجرای سفارش در BorsTerminal دارای قیدهای سخت‌گیرانه‌ای است که باید در بازطراحی فرانت‌اند ۱۰۰٪ حفظ شوند:

### ۴.۱. سکوی هدف و آداپتور EasyTrader / Orbis-MTS
* کارگزاری هدف سامانه **EasyTrader / Orbis-MTS** است (`execution_easytrader.py`).
* به دلیل اینکه پارامترهای پروتکل تلگرام و وب از روی مهندسی معکوس ۵ مخزن استخراج شده و هنوز توسط تست رسمی با حساب زنده تأیید قطعی نشده‌اند، متغیر `WIRE_HYPOTHESIS = True` در بک‌اند فعال است. واسط کاربری باید این وضعیت را با رنگ خنثی و توضیح شفاف نمایش دهد و هرگز ادعای واهی «تأییدشده» نکند.
* **پروتکل بدون تلاش مجدد (Zero Retry Policy):** آداپتور بک‌اند صراحتاً با `max_retries = 0` اجرا می‌شود. اگر یک درخواست به دلیل Timeout پاسخی دریافت نکرد، وضعیت آن **«نامعلوم» (`unknown_result`)** می‌شود. واسط کاربری موظف است در این وضعیت دکمهٔ «ارسال مجدد» را **غیرفعال** کرده و تنها دکمهٔ «رفع ابهام / تطبیق» (`POST /api/execution/reconcile/{id}`) را در دسترس قرار دهد.

### ۴.۲. قابلیت‌های کارگزاری و مسئلهٔ جایگاه صف (Queue Position)
بر اساس متد `capabilities()` در `execution_easytrader.py`:
```python
PROTOCOL_CAPS = Capabilities(
    place=True,
    list_orders=True,
    order_state=True,
    queue_position=True,  # وابسته به پاسخ /ms/api/MarketSheet/order-place
    cancel=False,         # در مستندات سیم احراز نشده
    best_bid_ask=False,
    balances=False        # کارگزاری موجودی نقد حساب را از این مسیر برنمی‌گرداند
)
```
* **سیاست نمایش موجودی (Balance Policy):** از آنجا که `capabilities.balances = False` است، واسط کاربری به هیچ وجه عدد صفر یا عدد ساختگی نمایش نمی‌دهد، بلکه عبارت صریح **«بی‌داده (کارگزاری موجودی را برنمی‌گرداند)»** درج می‌شود. سرانهٔ تابلوی بورس نباید به عنوان قدرت خرید کارگزاری معرفی شود.
* **سیاست جایگاه صف (Queue Position Policy):** در صورتی که آداپتور عدد صف را برنگرداند یا کارگزاری فیلد را خالی بگذارد، مقدار با **«—» (نامشخص)** نمایش می‌یابد و هرگز عدد صفر (که به معنی نفر اول بودن در صف است) جعل نمی‌شود.

### ۴.۳. قفل سه‌گانهٔ اجرای واقعی ربات (Triple-Lock for Live Bot)
ربات معاملاتی در `api/bot.py` به صورت پیش‌فرض در حالت کاغذی (`mode: paper`) قرار دارد. برای فعال شدن معاملهٔ زنده، هر سه شرط زیر باید هم‌زمان برقرار باشند:
1. `BORS_EXECUTION_LIVE=1` در متغیرهای محیطی سیستم تنظیم شده باشد.
2. قابلیت‌های آداپتور فعال حداقل شامل `place`، `order_state` و `list_orders` باشد.
3. وضعیت نشست کارگزاری در وضعیت `connected` باشد.

اگر حتی یکی از این سه قفل بسته باشد، سوئیچ معاملهٔ واقعی در فرانت‌اند غیرفعال مانده و دلیل مسدودی صراحتاً در زیر آن اعلام می‌شود.

## ۷. استراتژی مدیریت وضعیت و ناوبری متقابل (State Management & Cross-Navigation)

### ۷.۱. حل چالش وضعیت سراسری نماد (`symbolStore.ts`)
بر اساس یافته‌های فاز صفر (`PHASE-0-INVENTORY.md` §۴)، انتخاب نماد در BorsTerminal هم‌اکنون از طریق `shared/stores/symbolStore.ts` با یک کلید سراسری در `localStorage` به نام `bors-symbol` اداره می‌شود. اگر کاربر در دو تب یا صفحهٔ مختلف دو نماد متفاوت را انتخاب کند، وضعیت آن‌ها روی یکدیگر بازنویسی می‌شود.

**معماری پیشنهادی حل وضعیت:**
1. **اصالت مسیر (Route-Driven State):** مسیر باید منبع اصلی حقیقت نماد فعال باشد (`#/execution/:symbol?`).
2. **ارتباط پارامتر مسیر با تیکت سفارش:**
   ```typescript
   // در صفحه ExecutionPage:
   const { symbol: routeSymbol } = useParams<{ symbol?: string }>();
   const { activeSymbol, setActiveSymbol } = useSymbolStore();
   
   // نماد تیکت اولویت را به URL می‌دهد، سپس به استور سراسری
   const targetSymbol = routeSymbol || activeSymbol || 'فولاد';
   ```
3. **عدم بازنویسی ناخواسته:** تغییر نماد درون فرم سفارش سریع، صرفاً URL مسیر `#/execution/:newSymbol` را به‌روزرسانی می‌کند و استور سراسری `bors-symbol` را دستخوش تغییر لحظه‌ای برای سایر تب‌های مانیتورینگ نمی‌سازد، مگر اینکه کاربر صراحتاً دکمهٔ «انتخاب به عنوان نماد سراسری ترمینال» را کلیک کند.

### ۷.۲. ناوبری متقابل و انتقال آسان نماد (Cross-Workspace Navigation)
کاربر باید بتواند از هر نقطه‌ای از نرم‌افزار بلافاصله نماد مورد نظر را به میزکار سفارش سریع ارسال کند:
* **از صفحه تکنیکال (`/technical/:symbol`):** اضافه شدن دکمهٔ ترید سریع در نوار ابزار نمودار:
  ```tsx
  <Button onClick={() => navigate(`/execution/${symbol}`)}>
    ارسال به میزکار سفارش سریع
  </Button>
  ```
* **از جدول غربالگری فیلترهای تابلو (`/market`):** کلیک راست یا منوی شناور سطر تابلو: گزینهٔ «ارسال سرخطی».
* **از جعبه فرمان (`CommandPalette`):** دستور سریع `buy <symbol>` یا `sell <symbol>` مستقیماً صفحهٔ `#/execution/:symbol` را با قیمت آستانه باز می‌کند.

## ۸. سند تحویل و برنامه‌ریزی پیاده‌سازی (Handoff & Implementation Plan)

این طرح برای هماهنگی با مأموریت در جریان `_bors-ui-workstation` آماده شده است و مراحل اجرایی آن به شرح زیر پیشنهاد می‌شود:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        برنامه فازبندی پیاده‌سازی                       │
├────────────────────┬───────────────────────────────────────────────────┤
│ فاز ۱: زیرساخت     │ تعریف مسیرهای routes.tsx و درج در سایدبار اصلی     │
│ فاز ۲: جداسازی     │ انتقال کامپوننت‌های ExecutionPanel و BotPanel     │
│ فاز ۳: ارتقای تیکت │ بازسازی جدول پیش‌فرود و فرم سفارش بر اساس ۵ مرجع  │
│ فاز ۴: پایش ربات   │ پیاده‌سازی نمایشگر موانع سه‌گانه و لاگ نشست‌های ربات│
│ فاز ۵: تست و انطباق│ راستی‌آزمایی با گاردهای CI و شبیه‌ساز آفلاین کارگزاری│
└────────────────────┴───────────────────────────────────────────────────┘
```

### فاز ۱: ثبت مسیرها و ناوبری (Routes & Shell Integration)
1. اضافه کردن دو ورودی در `frontend/src/routes.tsx`:
   * `{ path: 'execution/:symbol?', element: page(() => import('@features/execution/routes/ExecutionPage')) }`
   * `{ path: 'bot', element: page(() => import('@features/bot/routes/BotPage')) }`
2. افزودن دو آیتم استاندارد با آیکون‌های متناسب به منوی کناری `Sidebar.tsx`:
   * برچسب «سفارش سریع» با مسیر `/execution`
   * برچسب «ربات معاملاتی» با مسیر `/bot`
3. اضافه کردن میانبرهای صفحه به `CommandPalette.tsx`.

### فاز ۲: تفکیک و کپسوله‌سازی ماژول‌ها (Modular Extraction)
1. انتقال ماژول‌های مرتبط با سفارش از `features/portfolio/` به پوشهٔ اختصاصی `features/execution/`.
2. انتقال ماژول‌های ربات از `features/portfolio/` به پوشهٔ اختصاصی `features/bot/`.
3. استخراج کلاینت‌های مستقل `orderClient.ts` و `botClient.ts` در لایه‌های مربوطه بدون وابستگی به صفحهٔ پرتفوی.

### فاز ۳: ارتقای تعاملی تیکت و دفتر سفارش (Interactive Ticket & L2 Depth)
1. پیاده‌سازی تیکت دو ستونه با قابلیت دریافت قیمت از آخرین مظنه.
2. احیای جدول تفکیکی پیش‌فرود (مشابه کامیت `5307a795`) با وضعیت لحظه‌ای پاسخ `orderApi.preflight()`.
3. اتصال دکمه‌های وضعیت به لجر دیسک پایدار و افزودن قابلیت نمایش لاگ کامل سفارش بدون تغییر صفحه.

### فاز ۴: تکامل میزکار ربات (Bot Control Dashboard)
1. پیاده‌سازی ویجت موانع سه‌گانهٔ اجرای زنده با نشانگرهای سبز/زرد/قرمز صریح.
2. طراحی جدول رادار نمادها و نمایش زندهٔ تصمیمات داور قیف FTS.
3. تجهیز صفحه به کلید قطع اضطراری نرم‌افزاری و دکمهٔ اجرای آزمایشی نشست.

### فاز ۵: آزمون و سنجش انطباق (Verification & Quality Gates)
1. اجرای گاردهای سیستمی:
   ```bash
   python dev/version_anchor_guard.py
   python dev/persian_glyph_guard.py
   python tools/guard_ci_sim.py
   ```
2. اجرای تست‌های کلاینت فرانت‌اند:
   ```bash
   npx vitest run
   npx tsc -b
   ```
3. سنجش بصری در دو رزولوشن 1366×768 و 2560×1440 با مرورگر آزمون زنده.

## ۹. واژه‌نامهٔ اصطلاحات و تعاریف استاندارد فارسی (RTL Terminology Reference)

برای حفظ یکپارچگی زبان محصول و پرهیز از به کار بردن ترجمه‌های نامأنوس، واژگان زیر در کلیهٔ بخش‌های UI تصویب شده‌اند:

| اصطلاح انگلیسی | معادل استاندارد در واسط کاربری BorsTerminal | مفهوم عملیاتی در سیستم |
| :--- | :--- | :--- |
| **Preflight** | **پیش‌فرود / اعتبارسنجی اولیه** | بررسی ۹ گانهٔ اعتبار پیش از خروج هرگونه ترافیک به سمت کارگزاری |
| **Prepare / Wire Preview** | **پیش‌نمایش بدنه ارسالی** | ساخت و نمایش بستهٔ JSON واقعی که قرار است به پروتکل Orbis-MTS ارسال شود |
| **Dispatch** | **ارسال قطعی سفارش** | خروج درخواست HTTP تک‌تلاشی بدون بازگشت به سمت کارگزاری |
| **Reconcile** | **رفع ابهام / تطبیق وضعیت** | استعلام لیست سفارش‌ها برای مشخص کردن سرنوشت سفارش نامعلوم در زمان Timeout |
| **Queue Position** | **جایگاه در صف خرید/فروش** | رتبه در صف با نمایش `—` در صورت عدم اعلام سرور (ممنوعیت استفاده از صفر) |
| **Halt / Kill Switch** | **توقف اضطراری / کلید قطع** | قطع فوری دسترسی معامله و ذخیرهٔ حالت قفل روی دیسک SQLite |
| **Paper Simulation** | **شبیه‌ساز کاغذی** | اجرای کلیه محاسبات و ثبت مجازی معامله بدون تولید ترافیک شبکه |
| **Live Execution** | **معاملهٔ واقعی** | ارسال سفارش به حساب کارگزاری در صورت گشایش هر سه قفل امنیتی |
| **Append-Only Ledger** | **دفتر کل پایدار اجرا** | پایگاه دادهٔ محلی غیرقابل بازنویسی برای نگهداری تمام گام‌های سفارش |
| **Wire Hypothesis** | **فرضیهٔ پروتکل کارگزاری** | پرچم هشداردهنده مبنی بر اینکه ساختار وب‌سرویس هنوز با حساب واقعی نهایی نشده است |
