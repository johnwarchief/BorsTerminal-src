# ادغامِ لایۀ jev-ui درِ تبِّ سرخطی — شواهدِ سازگاری، مسیرِ resolver، و هزینه

تاریخِ بررسی: 2026-10-19 · مخزن: BorsTerminal · شاخه: `mission/sarkhati-jev-ui-2026-10-19`
پایانۀ بررسی: `frontend 79.67 kB` Sarkhati chunk، `jev-ui@0.0.2`

این سند پاسخِ سه پرسشی است که اصلاحیهٔ مالک مطرح کرد: آیا `jev-ui` درِ این
معماری واقعاً کار می‌کند؟ مسیرِ امنِ resolver چیست؟ هزینه‌اش چقدر است؟ هر ادعا
یا عددی که ازِ اجرا نیامده، برچسبِ «سنجیده‌نشده» گرفته است.

---

## ۱) چه چیزی نصب شد و از کجا خوانده شد

| مورد | مقدار | منبع |
| --- | --- | --- |
| نسخۀ `jev-ui` | 0.0.2 | `npm view jev-ui version` + `package.json` |
| `peerDependencies` | `react >= 18` | `node_modules/jev-ui/package.json` |
| `dependencies` | `@typesafe-ai/sdk ^0.6.0` | همان |
| `type` / exports | `module`؛ `.` و `./action` و `./server` | همان |
| Reactِ پروژه | ^18.3.1 | `frontend/package.json` |
| ابزارِ پروژه | Vite 5.4.21، TS 5.9.3، Tailwind 4.3.3، SPA با Hash Router | `frontend/package.json` |

متنِ سورسِ بسته (نه README) خوانده شد: `dist/components/{Branch,Rank,Gate,provider}.js`،
`dist/hooks/{useDecision,useScore,useJevState}.js`، `dist/core/{policy,payload,state,batch,ids,types}.js`،
`dist/{server,action}.js` و `dist/transport/live.js`. مستنداتِ
`docs.jev-ui.dev` فقط ناوبریِ صفحه را برمی‌گرداند و متنِ نمونه ندارد؛ لذا مرجعِ
این سند سورسِ واقعی است. **نمونه‌های Next.js درِ این پروژه اجرا نمی‌شوند**:
`dist/action.js` خطِ اولش `'use server'` است و به Server Action وابسته است.

## ۲) سازگاریِ اثبات‌شده باِ معماریِ فعلی (بدونِ Next)

اجرا رویِ همین worktree، با `node_modules` مستقل:

| گیت | نتیجه |
| --- | --- |
| `npm install jev-ui@0.0.2 --save-exact` | موفق؛ دو بسته (jev-ui + SDK)، peerِ React ۱۸ بدونِ سازگاری‌شکندی |
| `npx tsc -b` | صفر خطا |
| `npx eslint src/features/portfolio src/__tests__/jev-ui-compat.spec.tsx` | صفر مشکل (قواعدِ `boundaries/*` و `no-restricted-syntax` شاملِ این کد است) |
| `npx vitest run` (compat) | ۹/۹ سبز |
| `npx vitest run` (رفتارِ سرخطی) | ۱۵/۱۵ سبز |
| آزمون‌هایِ از قبل موجودِ تب | ۷۸/۷۸ سبز، بدونِ تغییرِ یکِ تست |
| `npm run build` (vite) | موفق؛ دستورِ `'use client'` درِ ماژول‌هایِ ESM برایِ Rollup بی‌اثر است و خطا نمی‌دهد |

پس ادعای «سازگار است» ازِ اجرای واقعی می‌آید، نه ازِ peer range.

## ۳) درزِ حریمِ خصوصی که بسته خودش بسته است

`resolve` به‌صورتِ تزریقِ تابعی واردِ `JevProvider` می‌شود
(`JevProvider({ resolve, state, onStateChange, track, children })`)؛ هیچ مسیری
درِ آن «خودکار به سرویس می‌رود» وجود ندارد. کانال‌هایِ state سه تا‌اند:
`CHANNELS = ['app','recent_actions','time_spent']` و `app` را کاملًا خودِ
برنامه می‌سازد. `buildPayload` همین سه را می‌برد. نتیجه: سانسور درِ یک تابعِ
تک‌نقطه‌ای ممکن است، و درِ `lib/jevSarkhati.ts` هم همین کار را می‌کند
(`appStateForJev` فقط هفت کلیدِ غیرحساس می‌سازد).

کنترلِ سنسور (نه ادعایِ صرف): درِ `jev-sarkhati.spec.tsx` یک پاسخِ نمونه با
`account_label`، `adapter`، `ledger_size` و `blocked_on` ساخته می‌شود؛ تستِ
«کنترلِ مثبت» اول ثابت می‌کند آن رشته‌ها درِ خودِ پاسخِ سرویس واقعاً هستند، بعد
تستِ «نشت» ثابت می‌کند درِ `sent` payload نیستند. باِ جهشِ عمدی (برداشتنِ
سانسور) همان دو تست قرمز شدند و پس ازِ بازگردانی سبز شدند.

## ۴) مسیرِ resolver: چه چیزی ممکن است و چه چیزی نیست

| ترانسپورت | وضعیت درِ این محصول | چرا |
| --- | --- | --- |
| `live` | **غیرممکن درِ نسخۀ منتشرشده** | `createLiveTransport` تنها مصرف‌کنندۀ `@typesafe-ai/sdk` است؛ `server.js` آن را import می‌کند و `pickTransportName()` از `process.env` می‌خواند. باندلِ منتشرشده BorsTerminal Python (PyInstaller) + پوستۀ Tauri/Rust است و هیچ رانتایمِ Node ندارد. |
| `live` از ماشینِ توسعه | **مسدودِ شبکه** | یک درخواستِ داده‌تهیِ فقط‌خواندنی به `https://api.typesafe.ai/v1/systemone`: `HTTP 451`. میزبانِ کنترل (`https://api.github.com/zen`) همان لحظه `200` داد، پس قطعیِ سراسری نیست؛ همان بلوکی است که درِ پایلتِ قدیمی هم ۴۵۱ ثبت شده بود. |
| `record` | نیازمندِ `live` برایِ ساختِ fixture | همان ۴۵۱ |
| `replay` | fixture لازم دارد | fixture‌ای از این پروژه ساخته نشده؛ ساختِ دستی‌شان «پاسخِ ضبط‌شدهٔ ساختگی» می‌شود نه داوری |
| `mock` | سبز و بی‌کلید | ترانسپورتِ رسمیِ آزمونِ واحدِ خودِ بسته؛ آزمون‌هایِ اینجا باِ تابعِ کنترل‌شدهٔ مشابه کار می‌کنند تا CI بی‌هزینه و قطعی بماند |
| **ترانسپورتِ خودی (تزریقِ `resolve`)** | **انتخابِ این ادغام** | درزِ رسمیِ مستندات برایِ «route handler یا script»؛ بدونِ شبکه، بدونِ کلید، قطعی و قابلِ آزمون |

سه قیدِ مستقل دیگر هم همان نتیجه را می‌دهند، پس این تصمیم فقط به‌خاطرِ ۴۵۱ نیست:

۱. قیدِ مخزن (AGENTS.md): «هیچ داده‌ای از خودِ برنامه/ماشینِ کاربر بیرون نمی‌رود».
۲. قیدِ مأموریتِ سرخطی: اعتبارنامه، کوکیِ نشست و جزئیاتِ حساسِ سفارش نباید به
   سرویس Jev ارسال یا در telemetry آن ثبت شوند. برایِ تبِّ سفارش، مفیدترین
   ورودیِ یک داوریِ واقعاً تطبیقی همان نماد/قیمت/حجم/وضعیتِ نشست است؛ اگر آن‌ها
   نفرستاد، داوری چیزی برای دیدن ندارد. این تضادِ ساختاری است، نه کمبودِ پیاده‌سازی.
۳. کلیدِ API هرگز درِ bundle مرورگر یا فایلِ قابلِ انتشار نمی‌نشیند؛ درِ این
   محصول سرورِ میزبانی‌شده‌ای هم نیست که کلید را نگه دارد.

## ۵) چه چیزی ساخته شد

- `frontend/src/features/portfolio/lib/jevSarkhati.ts` — `appStateForJev`
  (سانسورِ تک‌نقطه‌ای)، `jevRuleAnswer` (جدولِ قاعده)، `resolveJevRules`
  (`ResolveFn`؛ `meta.transport = bors-rules-offline`، `requests: 0`، بدونِ
  `model`/`usage`/`costUsd`)، و `sent` از `buildPayload` تا payloadِ واقعیِ
  قابلِ دیدن باشد.
- `frontend/src/features/portfolio/components/sarkhati/SarkhatiProTools.tsx` —
  ردیفِ «ابزارهایِ حرفه‌ای» با `Rank`، خطِ راهنما با `Gate`، بلندیِ راهنما با
  `useScore`، dwell با `useTimeOnScreen` و `track`.
- `SarkhatiPage.tsx` — همان ردیفِ قبلی جایِ خودِ مؤلفه نشست؛ استایلِ چیپ‌ها به
  `chipClass` درِ `parts.tsx` منتقل شد تا دو نسخهٔ کلاس درِ صفحه نباشد.
- دو فایلِ آزمون: `jev-ui-compat.spec.tsx` (سازگاریِ کتابخانه) و
  `jev-sarkhati.spec.tsx` (رفتارِ همین تب).

### آنچه Jev UI تصمیم نمی‌گیرد (و تست‌ها همین را می‌بندند)

اعتبارِ سفارش، قیمت، حجم، مجازبودنِ ارسال، انتخابِ حساب، ارسالِ دوباره،
وضعیتِ پذیرش/رد/نامعلوم، و هیچ پیامِ امنیتی. داوری فقط دو چیز است: ترتیبِ سه
پنلِ *ثانویه* و دیدنی‌بودن/پربودنِ یک خطِ راهنمایِ *اضافه*. متنِ راهنما از
فیلدهایِ خودِ پاسخِ سرویس درِ `SarkhatiPage` ساخته می‌شود، نه از داوری.

### رفتارِ بی‌شبکه و بی‌کلید

همه‌چیز درِ پروسهٔ مرورگر می‌ماند؛ `fetch` هرگز صدا زده نمی‌شود (تست). اگر
`resolve` خطا بدهد: `Rank` ترتیبِ خام را نگه می‌دارد، `Gate` بسته می‌ماند، و
هیچ چیپی حذف نمی‌شود (تست). درِ `pending` هم راهنما نمایش داده نمی‌شود تا
چشمک نزند.

## ۷) وضعیتِ صادقانۀ ادغام

| لایه | وضعیت |
| --- | --- |
| کتابخانه درِ این SPA (Vite/React ۱۸/TS) | **SUPPORTED** — اثبات‌شده باِ tsc/eslint/vitest/build |
| `Rank`، `Gate`، `useScore`، `useTimeOnScreen`، `track` درِ تبِّ سرخطی | **SUPPORTED** — باِ قاعدۀ خودی، آزمونِ رفتار و کنترلِ منفی |
| داوریِ مدل‌محور (پاسخِ zنده ازِ سرویس Jev) | **BLOCKED-BY-SERVICE (HTTP 451)** و **DISALLOWED-BY-POLICY** (بیرون‌رفتنِ جزئیاتِ سفارش ممنوع؛ Node tier درِ باندل نیست؛ کلید درِ bundle ممنوع) |
| `replay` باِ fixture | **NOT_VERIFIED** — fixture ضبط‌نشده چون ضبط نیازمندِ `live` است |
| پاریتیِ بصریِ تب درِ مرورگر زنده | درِ بخشِ «راستی‌آزماییِ زنده» گزارش می‌شود؛ تا آن لحظه **UNVERIFIED** |

`JEV_UI_INTEGRATION = PARTIAL`: لایۀِ ارائه و زیرساختِ داوری (provider،
batcher، ماشینِ وضعیت، policy، Inspector، fallbackها) واقعی و درِ مسیرِ تولیدی
است؛ «مغز» شبکه‌ای روشن نیست و روشن نخواهد شد مگر مالک هم‌زمانِ سه قیدِ بالا
را تغییر دهد. هرچه درِ `meta.transport` و درِ همین سند نوشته شده همین را می‌گوید
و هیچ‌جا «ادغامِ کاملِ مدل» خوانده نمی‌شود.

## ۸) اگر روزی ترانسپورتِ زنده خواسته شود

۱. یک میزبانِ سمتِ سرور باِ `JEV_TRANSPORT=live` و کلید درِ محیطِ امن (نه درِ
   ریپو، نه درِ bundle) — امروز چنین میزبانی درِ این محصول نیست.
۲. مجوزِ صریحِ خروجِ داده ازِ ماشینِ کاربر، یا تعریفِ داوری فقط رویِ سیگنال‌هایِ
   غیرمرتبطِ با سفارش.
۳. رفعِ مسدودیِ جغرافیایی (۴۵۱) یا میزبانیِ proxy.
۴. درِ همین ساختار، تغییرِ کار فقط «جایِ `resolveJevRules` باِ `createResolver`
   درِ یک route handler» است؛ هیچ مؤلفه‌ای باید عوض نشود. همین جدا بودنِ مغز از
   ارائه، تنها دلیلی است که این ادغام باِ وجودِ ۴۵۱ بی‌فایده نشد.

## ۹) بازبینی‌هایِ باز

- آیا جابه‌جاییِ ترتیبِ سه دکمۀِ ثانویه برایِ مالک مطلوب است، یا حتی همان دو
  جایِ اول باید قفل بماند؟ (`pinTop` برداشته شد چون باِ آن، قاعدۀ «توقفِ اضطراری»
  عملاً هیچ جابه‌جاییِ معناداری تولید نمی‌کرد — این عدد درِ تستِ «کنترلِ منفی» پیداست.)
- راهنمایِ `Gate` فعلاً درِ حالتِ «گیر کردنِ تکراری» روشن می‌شود. آستانه‌هایِ
  dwell و تکرار، رأیِ مالک است، نه سنجشِ من.
- سند هیچ ادعایی دربارهٔ بهبودِ زمانِ ارسالِ سفارش نمی‌کند؛ این لایه به دروازۀ
  ارسال دست نمی‌زند.
