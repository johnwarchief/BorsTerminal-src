# سرخطیِ چندنمادی (P0) — قرارداد، پیاده‌سازی، سنجشِ زنده وِ آنچه باز است

**شاخه:** `mission/uiux-2-0-redesign-2026-10-16` · **تاریخ:** ۱۴۰۵-۰۷-۲۴ (۲۰۲۶-۱۰-۱۶)
**سطحِ کلیِ اینِ سند:** رابطِ چندتبّه رویِ بک‌اندِ **آزمایشی** (mock + dry-run) باِ سنجشِ زنده درِ مرورگر. هیچِ اتصالِ کارگزاری درِ اینِ دور آزموده نشده وِ هیچِ سفارشِ واقعی ارسال نشد.

---

## ۰) خلاصه درِ پنجِ سطر

1. درِ اینِ شاخه دروازۀِ `/api/execution/*` ثبت نبود: `status` وِ `session` وِ `bot` هرِ سه **۲۰۰ باِ `text/html`** (fallbackِ SPA) برمی‌گرداندند — «موفق» بی‌هیچِ قراردادی. دربارۀِ همینِ خطر، بندِ ۱.۱ مأموریت هشدار داده بود.
2. پاسخِ ۲۰۰ وِ نبودِ خطا نشانهٔ سلامتِ endpoint نیست: هرِ مسیرِ ثبت‌شدہ باِ `content-type` وِ باِ بدنهٔ خواندنی سنجیده می‌شود (`tools/ui_execution_contract_capture.py` → فیکسچرِ ضبط‌شده، **۲۰ مورد: ۱۹ `application/json` + ۱ `text/html`** که آنِ یکی عمدی است: مسیرِ ثبت‌نشده).
3. رابطِ چندتبّه ساخته شد که درِ آنِ هرِ تب نماد/قیمت/تعداد/جهت/حالت/شناسۀِ اجرا/نتیجه **مالِ همانِ تب** است؛ «ارسالِ گروهی» = چندِ درخواستِ مستقل باِ سقفِ هم‌زمانیِ خوانده‌شده ازِ `limits` (بی‌endpointِ گروهیِ ساختگی).
4. سه نقصِ واقعی ازِ همینِ سنجشِ زنده بیرون آمد وِ اصلاح شد (schemaِ غلطِ dispatch، دکمۀِ «آماده‌سازی» که شناسه را درِ سرویس قفل می‌کرد، ادعایِ الزامِ تأیید) — هیچ‌کدام باِ ضعفِ کردنِ آزمون سبز نشدند.
5. **ارسالِ واقعی همچنان BLOCKED است**؛ فهرستِ دقیقِ وابستگی‌ها درِ بندِ ۶ است. هیچِ قسمتی ازِ اینِ سندِ «قابلیتِ عملیاتیِ کامل» ادعا نمی‌کند.

## ۱) بندِ ۱.۱ — قراردادِ واقعی، آن‌طور که سرویس می‌گوید

### ۱-الف) انتقالِ انتخابی ازِ `main` (بی‌merge کورکورانه)

`api/execution.py` + `execution_contract/service/mock/timing/latency/ledger/easytrader` ازِ `main` بهِ اینِ شاخه منتقل شد (کامیتِ `dc63859`) — فایل‌ها دست‌نخورده، به‌جزِ ثبتِ router درِ `api/__init__.py` باِ همانِ ساختارِ شاخه وِ افزودنِ `hiddenimports` درِ دو `.spec`. **بک‌اندِ موازی ساخته نشد.**

| آنچه سنجیده شد | نتیجهٔ ضبط‌شده |
|---|---|
| شمارۀِ مسیرهایِ ثبت‌شدۀِ دروازہ | ۱۸ (`@router` درِ `api/execution.py`) |
| `/api/execution/status` | ۲۰۰ `application/json` · `adapter: mock` · `dry_run: true` · `live_enabled: false` · `nothing_will_leave_the_machine: true` |
| `blocked_on` (ازِ خودِ سرویس) | «آداپتورِ واقعی انتخاب نشده (BORS_EXECUTION_ADAPTER=easytrader)» |
| capabilities | `place/list_orders/order_state/queue_position/cancel: true` · `best_bid_ask/balances: false` |
| limits | `max_orders: 1` · `require_confirmation: true` · `max_orders_per_window: null` · `window_seconds: 60` · بقیۀِ سقف‌ها `null` |
| `/session` | `token_present: false` — هیچِ اعتبارنامۀِ ذخیره‌شده‌ای درِ پاسخ نیست |
| مسیرِ ثبت‌نشدهٔ `/api/*` | **۲۰۰ + `text/html`** — همانِ تله |

### ۱-ب) سه نقصی که فقط ازِ اجرایِ زنده دیده می‌شدند

**نقصِ ۱ — schemaِ دست‌سازِ UI باِ پاسخِ واقعی نمی‌خواند.**
`DispatchSchema` فرض کرده بود `kill_switch` شیء است وِ `execution_id` همیشه درِ پاسخِ موفق هست. واقعِ ضبط‌شده: `kill_switch: "ARMED"` (رشته) وِ درِ پاسخِ موفق `execution_id` **نیست**. اثرِ آن درِ UI: سفارشی که سرویس پذیرفته بود بهِ «نتیجهٔ نامعلوم» ترجمه می‌شد، چون zod خطا می‌داد.
**اصلاح:** `kill_switch: union(string, record)`، `execution_id` اختیاری، `payload_preview` وِ `.passthrough()`؛ وِ **تستِ رگرسیونِ سطح‌بندی‌شده**: `frontend/src/__tests__/order-line-contract.spec.ts` (۱۳ آزمون) همانِ پاسخ‌هایِ ضبط‌شده را ازِ دیسک می‌خواند، نه حدسِ رابط را.
**شاهدِ زنده پیش ازِ اصلاح:** `✗ نتیجهٔ همانِ تب ازِ پاسخِ سرویس خوانده می‌شود — {"code":"NOT_ORDERABLE", ...}` درِ اجرایِ اولِ `tools/ui_order_line_probe.mjs`.

**نقصِ ۲ — دکمۀِ «آمade‌سازی» شناسه را درِ سرویس می‌سوزاند.**
`POST /prepare` شناسۀِ اجرا را درِ `_prepared` رزرو می‌کند (`execution_service.py:383`) وِ آنِ رزرو هیچ‌گاه آزاد نمی‌شود. پسِ `prepare(x)` وِ بعدِ `dispatch(x)` ⇒ `DUPLICATE_GUARD` (شاهدِ ضبط‌شده درِ فیکسچر: `prepare_then_dispatch_same_id = error/DUPLICATE_GUARD/duplicate:FAIL`).
**اصلاح:** درِ رابط «پیش‌فرود ← مرور ← ارسال» ماند؛ `prepareOrder` درِ لایۀِ قرارداد وِ آزمونِ فیکسچر می‌ماند، ولیِ دکمه ندارد. یکِ تب نباید باِ یکِ کلیکِ بی‌ضرر، کلیکِ بعدی‌اش را رد کند.
**ثبتِ بالایی:** اگرِ `main` قصدِ مسیرِ دو مرحله‌ای دارد، آزادکردنِ رزرو درِ `execute()` کارِ آنِ مخزن است، نه اینِ شاخه (بک‌اند موازی نمی‌سازیم).

**نقصِ ۳ — «تأییدِ صریح» را دروازہ درِ `mode=safe` الزام نمی‌کند.**
`require_confirmation: true` است، ولیِ `dispatch(confirmed:false)` درِ حالتِ safe **موفق** برمی‌گردد (`dispatch_without_confirmed_flag = success`؛ منطق درِ `execution_service.py:361` فقطِ شاخۀِ `allow_repeat`/ULTRA را می‌پاید).
**اصلاحِ ادعا، نه داده:** رابط درِ همانِ کلیک `confirmed: true` می‌فرستد (تأییدِ صریحِ کاربر) وِ دیگر نمی‌گوید «بک‌اند الزام می‌کند». متنِ گیتِ صفحه ازِ پاسخِ سرویس خوانده می‌شود: «تأییدِ صریح: لازمِ است» — بدونِ نسبت‌دادنِ آن بهِ دروازہ.

### ۱-ج) نگاشتِ کارگزاری: رابط هیچِ شناسه‌ای اختراع نمی‌کند

`InstrumentRef.orderable()` سه دلیلِ رد دارد: `NOT_ORDERABLE:resolution` → `:isin` → `:broker_instrument`. درِ mock تنها باِ `mock_instrument: true`ِ **صریحِ درخواست** شناسۀِ بدل (`MOCK:<نماد>`) می‌چسبد.
رابط اینِ کلید را **فقط** وقتی نشان می‌دهد که خودِ سرویس `adapter: mock` اعلام کرده باشد (`gate.status?.adapter === 'mock'`)؛ درِ آداپتورِ واقعی هیچِ کلیدِ mock درِ DOM نمی‌نشیند (آزمونِ UI: «باِ آداپتورِ واقعی، رابط هیچِ کلیدِ mock درِ DOM نمی‌گارد»). تیک درِ هرِ تب جدا است وِ درِ بدنهٔ همانِ تب می‌رود (آزمونِ واحد).
دادهٔ بانکِ محلی (خوانده‌شده ازِ `market.db` همینِ شاخه): **۵۹۴۱ سطرِ `instruments`، ازِ آنِ میانِ ۱۵۴۷ سطرِ خالیِ ISIN** — نمادهایِ بی‌ISIN تاِ پُربودنِ بانک، بی‌تیک هم `NOT_ORDERABLE` می‌مانند. نمونهٔ زنده: `شپنا` → `رد · instrument · NOT_ORDERABLE:resolution`.

## ۲) بندِ ۱.۲ — چندِ تبِ واقعی باِ state مستقل

پروندۀِ تب: `frontend/src/features/execution/stores/orderLineStore.ts` (zustand) — هرِ تب `{id, symbol, side, mode, price, quantity, executionId, mockInstrument, phase, inFlight, checks, reasons, unknown, result, note}`. هیچِ فیلدِ مشترکی بینِ تب‌ها نیست؛ `tabSignature()` همین را آزمون می‌کند.

- **قفلِ ارسال درِ state است، نه درِ CSS:** `beginSend()` اتم است؛ دوِ کلیکِ همِ‌زمان درِ یکِ تسک، یکِ درخواست می‌سازد (سناریوِ ۹).
- **`executionId` درِ لحظۀِ ساختِ تب متولد می‌شود** وِ باِ ویرایشِ قیمت/تعداد عوض نمی‌شود — کلیدِ idempotencyِ همانِ پیش‌نویس می‌ماند.
- **بازیابیِ امن:** `sending/scheduled/dispatched` هنگامِ load بهِ `draft` برمی‌گردد باِ یادداشتِ روشن «ازِ نشستِ پیشین بازیابی شد؛ هیچِ سفارشی خودکار ارسال نمی‌شود». تنها «چیزی که کاربر تایپ کرده» + شناسه ذخیره می‌شود؛ نتیجه‌ها درِ ردِّپایِ سرویس‌اند.
- **APG Tabs** باِ `aria-controls` وِ roving tabindex؛ فقطِ پنلِ تبِ روشن درِ DOM می‌ماند (پسِ نمادِ اشتباهی بینِ دوِ پنلِ هم‌نام ممکن نیست).
- **واژگانِ وضعیت ازِ خودِ قرارداد است** (`draft/validated/prepared/scheduled/dispatched/acknowledged/rejected/cancelled/errored` + `unknown_result`) وِ `UNKNOWN` رنگِ `FAIL` ندارد.
- **خواندنی‌بودنِ `checks`:** دلیلِ رد برایِ `PASS` نمایش داده نمی‌شود — درِ پاسخِ سرویس برایِ چک‌هایِ قبول هم `reasons` می‌آید (`place: "broker cannot place orders"`) وِ نشان‌دادنش درِ کنارِ «قبول» دقیقاً همانِ ابهامی است که نباید ساخت.

## ۳) بندِ ۱.۳ — گروهیِ کنترل‌شده

`batchDispatch()` = حلقۀِ کارگر باِ `concurrency = min(limits.max_orders, ready)`؛ هرِ کارگر یکِ `tabDispatch()` مستقل باِ شناسۀِ همانِ تب. بی‌endpointِ گروهیِ ساختگی، چون خودِ دروازہ هرِ درخواست یکِ سفارش می‌گیرد.

مرورِ اجباری: دکمۀِ اول چک‌لیستِ `نماد · جهت · قیمت · تعداد · حالت · شناسۀِ اجرا` را باز می‌کند وِ «تأیید وِ ارسال» فقطِ پسِ آن درِ DOM می‌نشیند (آزمونِ UI + شاهدِ زنده). تبی که فرمِ کامل ندارد درِ صفِ نمی‌نشیند وِ علتش درِ همانِ مرور نوشته می‌شود (`order-batch-skipped-<id>`).

## ۴) بندِ ۱.۴ — زمان‌بندی باِ دوِ ساعتِ مستقل (گزارش، نه گیت)

اعدادِ اینِ جدول ازِ `_audit/ui2/order-line-probe.json` (همانِ اجرایی که درِ بندِ ۵ آورده شده) خوانده می‌شود: **پروسۀِ تازه‌آغازکرده، بی‌کشِ پاسخ**. دورۀِ پیشِ restartِ پروسه اعدادِ نزدیکِ همانِ بازه را داد (پیش‌فرود ۱۷/۱۹/۲۰، ارسال ۲۱/۲۲/۳۰، `dispatch_ms` ۸.۸/۱۰.۷/۱۲.۸) — یعنی تفاوتِ دوِ دور درِ حدودِ یکِ دورِ اندازه‌گیری است، نه یکِ جهش.

| مسیر | ساعتِ پروسه/مرورگر (min/med/max) | `timings` خودِ دروازہ | پاسخِ سرویس |
|---|---|---|---|
| `POST /preflight` (۵ نمونه، ازِ داخلِ مرورگر) | **۱۸/۱۸/۲۶ ms** | کلیدِ `timings` درِ پاسخِ preflight **نیست** | `ok: true` ×۵ |
| `POST /dispatch` (۵ نمونه، بی‌رابط) | **۲۲/۲۸/۳۴ ms** | `dispatch_ms: ۸.۸/۱۰.۷/۱۲.۸` (monotonicِ دروازہ) | `status: success` ×۵ · `kill_switch: ARMED` |

- `response_ms` وِ `observed_ms` درِ dry-run **null** هستند: چیزی بهِ کارگزاری نرفته تاِ RTT یاِ رتبۀِ صف اندازه گرفته شود. هرِ عددی که درِ اینِ حالت «سرعتِ ارسالِ سفارش» یا «اولِ صف» جا بزند، ساختگی است — وِ درِ اینِ محصول ساخته نمی‌شود.
- تفاضلِ دوِ ساعت (۱۰.۱ تاِ ۱۹.۲ ms) هزینهٔ حلقۀِ HTTP/سرریزِ JSON درِ همانِ ماشین است، نه شبکۀِ کارگزاری.
- timeout/قطعِ ارتباط: سناریوهایِ تزریقِ خطا درِ بندِ ۵ (سطحِ UI) نتیجه را «نامعلوم» نشان می‌دهند، نه «رد»؛ وِ رابط برایِ مطابقت ازِ `POST /reconcile/<همان_شناسه>` استفاده می‌کند (شاهد: `مسیر=/api/execution/reconcile/x-…` وِ `dispatchِ تازه=۰`).
- محدودیتِ نرخ: `max_orders_per_window: null` باِ `window_seconds: 60` یعنی درِ اینِ پیکربندی سقفِ پنجره‌ای **بسته است**؛ شمارشِ `orders_in_window` برایِ دادهٔ واقعی معنایی ندارد. عددِ موردنیازِ مالک درِ بندِ ۶ آمده.

### ۵-ب) restart — آنچه سبز نیست وِ پنهان نمی‌ماند

`ExecutionLedger.open_ids()` (`execution_ledger.py:192-209`) فقطِ حالت‌هایِ **نبسته** را بازمی‌گرداند: `unknown_result / dispatched / acknowledged / scheduled / reconciled`. رُکوردِ بدل باِ `status: validated` درِ اینِ فهرست نیست؛ پسِ restartِ پروسه ازِ دیسک برنمی‌گردد وِ همانِ شناسه دوباره قبول می‌شود (مشاهده: **۲۰ سطر → ۰ سطر؛ replay = success**).

- چی محافظت می‌شود: سفارشِ **واقعی** باِ نوعِ `dispatch` ثبت می‌شود، درِ `open_ids()` می‌ماند وِ پسِ restart دوباره درِ `duplicate` می‌نشیند — یعنی خطرِ «سفارشِ معلقی که نمیدانیم کجا رفت» پوشش دارد.
- چی محافظت نمی‌شود: رزروِ شناسه‌هایِ dry-run. درِ mock بی‌ضرر است، **ولیِ اگرِ روزی آداپتورِ واقعی باِ dry_run روشن باشد وِ رکوردی `validated` بماند، اینِ همانِ سوراخِ دوبارارسالی است.**
- قفلِ خودکارِ همینِ رفتار: `test_execution_recovery.py` (۳ آزمون، بک‌اندِ سطحِ واحد) — سطرِ `validated` باز نیست؛ سطرِ `unknown_result` باِ نوعِ `dispatch` باز است؛ order_stateِ `filled` آنِ را ازِ فهرستِ باز بیرون می‌برد.
- شاهدِ کامل: `_audit/ui2/order-line-tired.json` (روشِ تکرارپذیر باِ دوِ دستور).
- درِ رابط، تنها راهِ ارسالِ دوباره پسِ restart یکِ کلیکِ آگاهانه است؛ هیچِ مسیرِ خودکاری وجود ندارد (پرابِ [۱۰]: صفرِ نوشتار).
