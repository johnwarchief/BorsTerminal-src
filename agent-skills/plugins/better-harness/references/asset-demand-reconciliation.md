# Asset Demand Reconciliation

Audience: lead only (Step 2.4); specialists never load this reference.

Use this reference only after the three specialists return and before the lead
freezes final findings. Join Session demand with Agent Customize coverage; do
not send either specialist the other's brief.

## Evidence Boundary

- Session may support repeated **procedure demand** or **knowledge demand**.
- Agent Customize may support asset presence, content quality, routing,
  integrity, scope, provenance, use, and outcome states.
- Project Evidence may identify the current owner or executable route. It does
  not prove a user/global asset was selected or used.
- An absent asset and an uncovered repeated demand are different facts. Keep
  the gap `Unobserved` until both sides are comparable.

Do not inspect raw prompts, Memory bodies, plugin caches, or another provider's
home, and do not create, install, enable, consolidate, or delete an asset.

## Select the Smallest Durable Owner

For each supported demand, ask what must persist:

| Demand shape | First owner route |
|---|---|
| Stable trigger, ordered procedure, output, stop, and verifier | [Skill Discovery](../../../references/agent-customize/skill-discovery.md) |
| Concise correction, decision, preference, or recurring trap | [Memory Review](../../../references/agent-customize/memory-review.md) |
| Current project fact, invariant, policy, or architecture boundary | Rule, `AGENTS.md`, spec, runbook, or project documentation |
| Deterministic transform or lifecycle enforcement | Script, Hook, Gate, Workflow, Agent, or another owner selected by Loop Discovery |
| External access without a reusable procedure | MCP/app/connector capability, not automatically a Skill |

Use [Loop Discovery](../../../references/loop-engineering/loop-discovery.md) when
the durable owner is unresolved. Before creation, apply: observed capability ->
host built-in -> configured owner -> extend -> create -> needs more evidence.

## Optional Skill Recommendation

Session Evidence may return either of two privacy-safe leads:

- **Reuse:** comparable Episodes repeat a task or capability demand while
  task-linked use of a relevant Skill is absent, sparse, or unresolved.
- **Codify:** comparable Episodes repeat a stable procedure with an ordered core,
  output, and validation or stop boundary.

Either supported lead requires the lead to apply
[Skill Recommendation](skill-recommendation.md). The first route asks
whether an actual built-in or configured Skill deserves a bounded trial. The
second asks whether current ownership is complete or the procedure should be
extended, created, or kept in a non-Skill owner. A reuse lead does not need to
prove a new workflow before existing coverage can be tried; extend/create still
requires the stronger codification evidence.

Global usage totals, names, paths, catalog labels, search misses, and asset
counts may route inspection but never create a lead or decide the answer.
Unknown Episode content, provider replicas, and benchmark sessions do not prove
production demand. Benchmark and replay evidence may test the reference but
cannot justify an organic recommendation.

Freeze the repeated demand before exposing inventory or expected actions. Then
compare it with actual owner instructions, runtime availability, task-linked
use, and declared omissions. Add only relevant SDLC catalog
rows as routing metadata; catalog presence or absence never decides coverage.
The recommendation cannot inspect outside supplied evidence, create assets, or
assign scores. It returns a disposition for the lead; a fully verified reuse
route becomes an ordinary `Low` finding in Step 3, never a separate suggestion.
If required evidence is unavailable, stop a normal durable report with the
missing condition; quick analysis keeps the gap explicit.

## Decide Whether a Memory Gap Exists

Require at least two independent comparable Episodes that repeat the same
correction, decision, rediscovery, or avoidable trap. Confirm that current
project truth does not already own it and the coverage map has no current,
retrievable owner. Then define the smallest provenance-bound lesson and a later
retrieval/application check.

Inventory count, one title collision, a short `AGENTS.md`, or one failed task
cannot prove missing Memory. A Memory candidate remains an opportunity until a
later episode supports retrieval, relevance, application, and outcome.

## Decide Whether a Skill or Plugin Trial Is Useful

A repeated procedure may enter Skill Discovery only when its trigger, inputs,
steps, output, validation, and failure boundary are stable. Existing installed
or built-in coverage wins unless evidence shows the missing behavior.

For a Plugin or packaged Skill, preserve this evidence ladder:

```text
available -> installed -> discovered -> selected -> invoked
-> task-relevant -> accepted outcome -> later comparable improvement
```

A fresh-task trial can establish discovery, activation, invocation, and
task-level usefulness. It cannot alone establish durable Loop Effectiveness or
justify replacing another package. Record missing steps and comparison scope.

## Lead Disposition

For each joined candidate, retain whether demand and coverage are comparable,
the current/smallest owner, the missing behavior, evidence state, and lead
decision. This is working state, not a new specialist schema or report artifact.

Only after this disposition may the lead phrase a recommendation. A reuse
disposition is finding-ready only when task-linked Skill-use evidence is complete
enough to distinguish no effective relevant use from unknown use, actual
instructions match the frozen demand, runtime availability is current, and the
Episodes show a present consequence. The trial needs a trigger, expected output,
verifier, and stop condition. Keep
creation, installation, cleanup, or write-back behind separate task-local
authorization and a named verifier.
